# Judge 6：Mobile UX 评审报告

## 评审视角

我是移动端体验评委。我的屏幕是 375–430px 的手机和 768–834px 的平板；我关心的是触控目标、拇指区、单手可达性、移动端首屏的信息密度、以及移动端性能预算是否现实（JS 体积、Canvas、字体加载在 4G + 中端安卓上的真实表现）。

**我的一票否决区：`mobile_experience` 与 `performance`。** 这两个维度我按最严标准打分，且它们对我的 Top 3 排名有一票否决权——一个桌面惊艳但移动端只是"响应式收缩"的方案，不可能进入我的前三位。

本次评审我带六个问题逐案核查：

1. **移动端是"真重设计"还是"响应式收缩"？** 看的证据是：信息优先级是否重排（不是同构堆叠）、是否有移动端特有的信息架构或交互替代物、断点行为是否有具体到 px 的描述。
2. **Command palette / 键盘和弦 / hover 重排在触屏上的替代方案是否完整？** 桌面签名交互没有触屏等价物 = 移动端体验残缺。
3. **大字号 display 在窄屏是否断行灾难？** 我对每个首屏大字在 335px 可用宽度（375 − 2×20 边距）做了字符宽度估算。
4. **移动端导航的具体形态**——"塞进 hamburger"直接扣分；全屏目录页、检索优先、bottom sheet、脊线指示等有观点的形态加分。
5. **移动端性能预算是否现实？** 字体家族数量 × 子集体积、Canvas 节点数与帧预算、lazy 策略、LCP 目标是否可信。
6. **站点内搜索在移动端如何触达？** 无搜索不是本轮扣分项（8 个 section 的站可以没有），但 5 年内容生长后没有搜索入口是长期风险，计入 `long_term_maintainability`。

每个方案我都做了 **375px 走查**（首屏看到什么 / 第一屏滚动后看到什么 / 到达 Research 与 Work 需要几次交互），写在逐方案评语末尾。

## 逐方案评语

### Team A — Minimalism「Monograph 单行本」

**优点：**

1. **§11 是全场少数把"你在哪"当移动端信息架构问题来解的方案**：桌面 sticky 左栏承担的方位感，移动端交给顶栏下方的 mono 章节指示器 `02 — RESEARCH`（IntersectionObserver 驱动，150ms fade）——这不是缩小桌面，是把桌面的一个子系统替换成了另一个子系统。`Index` 文字按钮打开的全屏总目录页（display-2 大字 + mono 章节号、无 stagger、Esc/点击关闭）是"把整站目录做成一页"的正解，与汉堡图标划清界限。
2. **移动端排版有明确立场**：正文 17/30 **大于**桌面（为拇指阅读重设）、Work 行改两端对齐两行式（mono `01 ——— 2025`）、整行 48px 触控目标、Lab 滑杆换 44px 原生 range + accent 方块 thumb。每个断点行为都给到了具体值。
3. **性能是全场最干净的**：零 Canvas、零视差、Hero 是纯文字（LCP = 首行文本，<1.2s 的目标是全场唯一"躺着也能达成"的）、字体 3 家族 ≤260KB、路由级代码分割。动效预算 ≤3 个同屏元素在移动端尤其值钱——低端机上唯一常驻动画是一个 caret。

**缺点/风险：**

1. **375px Hero 断行隐患（走查实测）**：display-1 下限 40px 时，"Retrieval-Augmented"（19 字符 × ≈0.52em × 40px ≈ 395px）超出 335px 可用宽，只能在连字符处断为 "Retrieval-" / "Augmented"——三行构图被动变四行。断点本身干净（有连字符兜底），但桌面精心设计的"第三行右缩进的斜向张力"在最小屏上消失。方案应明示 375px 下的行结构预案（例如移动端改为 "Retrieval-" "Augmented," "Generation," "before it breaks." 四行的主动构图）。
2. **无站点搜索**：单页锚点 + Index 目录在 9 个 section 时够用，但 Brief 要求 5 年内容生长（Notes > 20 篇拆路由页后），Index 页 + 无搜索的导航成本会上升。至少应预留一个"Notes 全量索引"的出口。
3. **全屏 overlay 无遮挡层 design 细节**：9 个 display-2 章节行（44/54px）在小屏（iPhone SE 375×667）一屏放不下 9 行 + Close，需要 overlay 内滚动——文档未说明 overlay 内部的滚动与焦点圈闭行为（对比 D 的"焦点困在层内"有明确交代）。

**最值得被偷走的想法：移动端"章节指示器"**——用一个 10px mono 行承担全站方位感，成本近乎零，且是任何桌面 sticky 侧栏方案在移动端的正确翻译。C 的左缘索引轨、F 的脊线 tick 都是它的近亲，但 A 的版本文字最明确。

**375px 走查**：首屏 = 顶栏（橙 tick + 名字 + `Index`）+ Hero 三行大字（~41px）+ lede + 两个锚点链接，纯文字首屏在 4G 上 <1.2s 可信。第一屏滚动后 = 章节指示器 + About 三句话。到达 Research = 滚动 ~1.5 屏，或 `Index` → 点击章节 = 2 次交互；到达 Work = Hero 上 `Selected Work ↘` 锚点 1 次点击。黄金路径全场最短之一。

### Team B — Editorial「Field & Retrieval 学刊」

**优点：**

1. **移动端 demo 的"只读回放"模式是全场最聪明的触屏替代之一**（§11）：Lab 画布在移动端提供"预置一次投毒的动画序列按钮化"——承认小屏操作过载，把交互 demo 降级为可回放的叙事，而不是硬塞全部控件。这是"移动端特有体验"的正确生成方式：不是加东西，是换一种参与方式。
2. **marginalia 的印刷式降级教科书级**：桌面右栏边注在移动端改为"被批注段落后插入上下 hairline 的行内旁注块（mono 12/16）"——保住"次要信息被分流"的层级，用印刷业一百年前就验证过的方式。对比多数方案直接丢弃边注内容，B 保留了信息。
3. **长文移动阅读链路完整**：文章末"翻页区"（`← PREVIOUS NOTE` / `NEXT NOTE →` 两行大字 index）、长文页底部 sticky mini-folio（当前 crosshead 名 + 进度线）、正文 17/28、drop cap 用 `::first-letter` 零 JS——一个移动端长读者的完整闭环。

**缺点/风险：**

1. **字体载荷是移动端最重的一份文字栈**：Fraunces（全轴可变）+ Newsreader + Instrument Sans + IBM Plex Mono 四家族，自估 ≈260KB woff2。移动 4G + 中端机上，四个 swap 字体的错峰替换 = 首屏三次以上 reflow/视觉跳动；且 Fraunces 的 opsz/WONK 轴若不做动态子集（masthead `text=`），实际体积会破预算。方案自己在 §14.3 承认了，但对策（按 unicode-range 分片）对四家族并行加载帮助有限。我的 `performance` 分因此从 8 压到 7。
2. **WONK hover 在触屏上是死代码**：签名交互在移动端无等价物（纯装饰可缺席，不算残缺），但这也意味着移动端用户与桌面用户看到的是两个不同性格的首页——刊物隐喻的核心表演只在桌面存在。
3. **刊名 72px 上限在大手机上的余量**：clamp(44→72px) 在 430px 宽的 Pro Max 上，"Retrieval"（9 字符 Fraunces opsz144 w540 ≈ 0.55em）≈ 356px，可用宽 430−40=390px——贴地飞行。若文案换成长刊名（用户未来自定义），会溢出。需要一个"刊名超长时降档到 56px"的规则。

**最值得被偷走的想法：移动端 demo"只读回放"模式**——为触屏把交互式 demo 重新叙述成一段可回放的序列，而不是砍功能或硬缩。所有含桌面签名交互的方案（C 的 Relevance Lens、E 的装置）都该为触屏写一份这样的"回放脚本"。

**375px 走查**：首屏 = folio bar（56px）+ 日期行 + 刊名两行叠放（~44px）+ 单条 2px 规则线 + standfirst 全宽 + dateline——"这是一本刊物"在移动首屏完整成立。第一屏滚动后 = Cover Story 标题（32–44px）+ deck 导语。到达 Research = 滚动 ~1 屏（Cover Story 即 Research Part II），或 `Contents` → 点击 = 2 次；到达 Work = 滚动 2–3 屏或 Contents → 2 次。

### Team C — Modern AI「精密仪器」

**优点：**

1. **全场唯一一个把两个签名交互的触屏替代都写完整、写成制度的方案**：⌘K → 移动端是"抽屉顶部检索输入框（=Palette 移动形态）"+ 顶栏检索图标；Relevance Lens hover 重排 → 长按 400ms 触发一次演示，或完全降级为展开行内的 `RELATED: P-01 Δ0.67` 文本（rMD 友好）。且给出了完整的禁用条件清单（`hover: none`、reduced-motion、条目 >12）——这是把触屏当第一公民写的设计。
2. **移动首屏是真正的信息架构重排**：SYS 状态块收为 2 行、关键词矩阵改单列 3 行（hover→点击展开 + 二次点击 affinity 高亮）、**pipeline 图转竖排"瀑布读数"**——读数点仍沿垂直连接线流动。这是移动端独有的构图，不是桌面的压缩版。
3. **Dossier bottom sheet + 左右 swipe 翻阅是移动端最对的档案形态**：拖把手、85vh 上限、下滑关闭、sheet 内 swipe 切换上/下一个项目——"把 ledger 变成可翻阅的档案夹"，把桌面的手风琴翻译成了移动端的空间隐喻。触控纪律成文（≥44px、mono-tag 移动端不缩水、左缘轨不渲染、刻度减为 2 枚）。

**缺点/风险：**

1. **375×667 首屏内装不下全部重排件**：mono tag 行 + 40px 标题（"Retrieval, made robust." 约 23 字符，会断为两行，断行干净）+ 2 行 SYS + 3 行矩阵 + 竖排 pipeline 五段——加总高度估算 >100svh，竖排 pipeline 必然探出首屏。方案未说明首屏的取舍优先级（哪一件先被推下去），需真机定稿。
2. **长按 400ms 与系统手势冲突**：长按在移动端默认语境是文字选择/呼出菜单——400ms 阈值恰好卡在 iOS 长按呼出放大镜/Android 文本选择的边缘，且 `-webkit-touch-callout` / `user-select` 处理未提及。好在有完整的文本降级出口，风险可控但需真机调参。
3. **Noto Sans SC 切片 + Inter + Plex Mono 三栈在移动首屏的叠加**：中文切片按需加载策略正确，但 `size-adjust` 校正 fallback 抖动未覆盖 CJK——中端安卓上 PingFang/MiSans 缺失时黑体 fallback 与 Inter 的基线错位会晃。11px mono-tag 全大写在移动端保持不缩是立场正确的，但 11px 大写 mono 在户外强光下的可读性堪忧（非 AA 问题，是环境问题）。

**最值得被偷走的想法：bottom-sheet Dossier + swipe 翻阅**——项目详情在移动端不是"新页面"也不是"手风琴"，而是一层可滑动关闭、可左右翻阅的档案抽屉。这是把"台账"数据结构翻译成移动空间隐喻的最优解，E 的 Bench Row 和 F 的展开面板都值得换成这个形态。

**375px 走查**：首屏 = tag 行 + 两行大标题 + SYS 两行读数 + 单列关键词矩阵（点击展开）+ 竖排 pipeline 上段。第一屏滚动后 = pipeline 下段 → README → Research ledger。到达 Research = 顶栏菜单 → 编号列表点击 = 2 次，或抽屉顶部搜索框输入 = 2 次；到达 Work = 滚动或同上。**移动端搜索触达是全场最顺滑的之一。**

### Team D — Academic「Offprint 抽印本」

**优点：**

1. **边注的三段降级是全场最完整的"桌面独有组件"移动化方案**（§6.2）：桌面漂浮边注 → 平板行内嵌入注（左侧 2px wash 竖线）→ 移动端可折叠行内注（正文内 `[3]` 上标按钮、44px 触达、`aria-expanded`/`aria-controls` 完整、无 JS 时 `<details>` 原生降级）。三档全部给到了实现机制，且"编号可见、内容按需展开、展开态有竖线标识"是被定义过的交互——不是"移动端隐藏边注"了事。
2. **Research 是 §01，移动端黄金路径零导航成本**：问题台账就在首屏滚动后第一屏，折叠态显示编号 + 问题 + 状态——研究者访客在手机上滚动两下就完成"这个人在想什么"的判断。375px 走查全场最优。
3. **为移动端单独画了一张竖版研究地图**（viewBox 0 0 360 760：RAG 居顶、Poisoning→Security 沿左列、Systems 沿右列，两套 SVG 都在 DOM 按断点显示其一）——不是把 920×560 的桌面图 squeeze 进小屏，是重新构图。加上 320px 与 1024px 两档的显式校验承诺，走查纪律全场最佳。

**缺点/风险：**

1. **CJK 衬线在移动端是双重风险**：Noto Serif SC 全量 >8MB、unicode-range CDN 切片救首屏——但移动端弱网下切片串行加载，回退 SimSun 的瞬间（方案自认）气质崩坏，而移动设备恰是 SimSun 缺失/替换字体（MiSans/HarmonyOS Sans 无衬线）最普遍的环境：衬线回退到无衬线的视觉断裂比桌面更刺眼。
2. **两套完整 SVG 地图同入 DOM**：桌面横版 + 移动竖版都渲染再按断点隐藏——对性能影响小（inline SVG），但对维护是真成本（节点数据变更要同步两套坐标），且方案自认地图坐标"是排出来的不是算出来的"。5 年问题数增长后双图手校是事故源。
3. **无搜索 + 60ch 长文在移动端的翻页成本**：Question Ledger 展开追问后，单条问题占屏幕大半，8 个 section 的单页在手机上总长可观；Contents 层有状态摘要（`5 questions · 4 cases · 3 notes`）很好，但从 §05 跳回 §01 仍需打开目录。对阅读型站点可接受，计入长期缺口。

**最值得被偷走的想法：`[n]` 上标按钮的可折叠行内注**——桌面边注内容在移动端不是消失而是变成"编号可见、点击展开"的第二阅读层，且用 `<details>` 保证无 JS 尊严。任何有 marginalia/脚注/旁注的方案（B、A 的 mono 旁注）都该抄这套三段降级。

**375px 走查**：首屏 = kicker + 立场句 44px（~4 行，28ch 语义断行）+ lede + 两个入口链接（`↓ §01`）。第一屏滚动后 = **§01 Question Ledger 折叠行**——到达 Research = 滚动即达（0 次导航交互）；到达 Work = 继续滚动 1 屏。全场黄金路径冠军。

### Team E — Creative Dev「BENCH 工作台」

**优点：**

1. **全场唯一正面强攻"移动端 Canvas"这个最难题目且给出可信工程预算的方案**（§2.2 性能表）：移动 ≤90 节点（按 `min(breakpoint, deviceMemory≤4GB)` 减载）、帧预算 14ms、DPR 上限 2、文字 sprite 预渲染、邻接对构建期算完、`visibilitychange` + IntersectionObserver 双停机、连续 30 帧 <45fps 自动降级半速 + 隐藏连线、`touch-action: none` 只限 canvas 内部不劫持页面滚动。这是把移动性能当验收标准写，不是当愿望写。
2. **"移动端以检索为第一导航"是全场最正确的移动导航判断**：`g` 和弦在触屏无意义 → 直接废除并以全屏 palette 替代；快捷键提示触屏自动隐藏；底部"工具坞"只放检索 + 主题两钮（拇指区）；菜单 bottom sheet（44px 行高 + safe-area）。对触屏的诚实在铲除桌面遗产，而不是搬运它。
3. **Lab 三台装置"选题时即约束不用 hover 依赖型 demo"**——移动端交互脚本全部成立（44px 滑杆拇指、双栏转纵向、得分条横向占满）。在源头消灭触屏死角的意识，比事后写降级方案高一个段位。

**缺点/风险：**

1. **主张行 44px 无语义断行设计（走查实测）**："Retrieval, perturbed, made robust." 在 335px 可用宽下约折 3–4 行，断点随机（"Retrieval, perturbed," / "made" / "robust." 之类的碎片），与 A 的刻意三行、F 的主动降级相比，E 的首屏大字没有为窄屏做过构图。加 `text-wrap: balance` 或手动 `<br>` 排布即可修复。
2. **性能方差仍是全场最大的**：预算写得再严，Canvas 文字渲染 + 触摸 spring 在 4 年前的中端安卓（Snapdragon 6 系）上仍是赌博——降帧路径存在意味着它自己也不确信能守住 60fps。另外"移动 ≤90 节点"只是数字，未给移动端单独的视觉构图（90 个词点在 375px 宽的场里密度如何、文字 sprite 的字号在 320px 是否可读，未验证）。Lighthouse ≥90 是模拟器指标，真机中位数的 P75 未承诺。
3. **Specimen Sheet 的移动堆叠与 segmented control 的横向滚动**：`Demo / Code / Notes` tab 转为 scroll-snap 横滑 segmented control——横向滚动区域在移动端是已知的可发现性黑洞（用户不知道右边还有）。需要渐变遮罩或溢出指示，文档未提。

**最值得被偷走的想法：`deviceMemory` + `hardwareConcurrency` 双探针的节点减载与自动降帧**——E 把"低端设备自动降级"写成了带验收指标的机制而不是一句"注意性能"。所有含 Canvas/重动效的方案（G 的 First Light、H 的 blur）都该抄这张预算表的结构。

**375px 走查**：首屏 = 眉行 + 主张行 44px（3–4 行被动断行）+ 副行 + P-00 装置（420px 高、lazy、标题先渲染后淡入）——装置占据首屏下半，好在"标题先渲染、关键信息不依赖装置"。第一屏滚动后 = 01 Work bench rows。到达 Work = 滚动 ≈1 屏；到达 Research = 滚动 2–3 屏，或检索图标 → 全屏 palette = 2 次。

### Team F — Swiss「Coordinate System」

**优点：**

1. **"12 列坐标纸塌缩为 1 根脊线"是全场最优雅的单个移动端翻译**（§11）：左缘 20px 处一根贯穿全页的 1px hairline + 8px 红 tick 随滚动移动（transform only）——暴露网格的体系感没有在移动端消失，而是退化为一根轴。"所有 section 编号 01–08 保留为 mono 前缀"是体系感的最小载体。这是把设计理念（而非视觉皮毛）移植到移动端的范本。
2. **375px 断行处置全场最佳**：海报大字移动端 clamp 56–72px、**最多 2 行**（`RETRIEVAL` / `& SYSTEMS`），"GENERATION" 主动移入标注行——这不是缩放，是重排；十字准星简化为一条水平线 + 红方块；并自查了"项目标题过长会破行"的风险（T4 降到 20px + `text-wrap: balance`）。 Poster 层使用规范（§3）甚至明文禁止"移动端首屏之外的任何位置"使用 Poster 字号——制度化的断行纪律。
3. **性能预算全场最轻**：Inter Tight + Inter + Plex Mono + Noto Sans SC <120KB（全场最低）、hairline 用 border + 绝对定位容器（明确禁 box-shadow 线）、动效仅 transform/opacity、Lab 画布与图版 lazy、触屏下坐标读数显示静态末值（不算动效）。移动端 60fps 几乎是免费的。

**缺点/风险：**

1. **无搜索 + 表格语法的内容深度，在移动端放大了"档案感 vs 使用感"的张力**：索引表 5 列在 375px 塌缩为两行堆叠（方案给了具体规格），但展开详情是 320–420px 的行内面板——在手机上，一个项目的"图版页"只有半屏高，Case Study 深度不足；F 是八个方案里唯一没有独立详情页路由的，移动端读一个项目的完整故事最费劲。
2. **脊线 tick 的信息量边界**：红 tick 指示"当前 section 的相对位置"，但 8 个 section 在一根 667px 高的轴上，每段 ≈80px——拇指扫一眼难以分辨 tick 在 03 还是 04（方案未给 tick 旁的当前 section 名标签；对比 A 的 `02 — RESEARCH` 文字指示器，F 的位置感是图形的、不读字的）。
3. **`INDEX` 全屏目录的 stagger 滑入（240ms）与目录大编号**：目录项 T2/T3 级 + 红色 mono 数字在触屏上的行高未明示（对比 A 的 display-2 行、D 的 h2 级 + 44px 触达承诺）——大概率没问题，但走查需要确认每行 ≥44px。

**最值得被偷走的想法：GENERATION 的处置方式**——把放不进移动首屏的 display 大字**降级进标注行**而不是缩小硬塞。这是对"窄屏断行"的正确价值观：宁可降信息层级，不做被动断行。所有首屏有长英文大字的方案（A、E、G、H）都该学这个动作。

**375px 走查**：首屏 = 简化顶标尺 + 海报 2 行（56px）+ 红方块与单水平线 + 兴趣索引两行 + `SCROLL ↓`。第一屏滚动后 = 01 Research R-INDEX 登记表。到达 Research = 滚动 ≈1 屏；到达 Work = 滚动或 `INDEX` → 1 次点击。黄金路径与 D 并列第一梯队。

### Team G — Dark Premium「Dimmer Room」

**优点：**

1. **移动端 Work 版式的"标题在媒体之前"有真正的移动推理**（§8）：先给语境再看展品，"避免滑动中图片突兀弹出"——这是从拇指滚动的心理模型出发的排序，不是桌面 zigzag 的机械堆叠。spec 表在移动端折叠为"label 行 + value 行"两行制也有具体规格。
2. **移动端性能意识有真实动作**：First Light 缩短为 0.9s + 光晕半径 −30%（省电）、图片 `srcset` 两档、Playground demo 首屏外全部 lazy chunk、`matchMedia('(pointer: coarse)')` 下禁用 blur > 8px、hover 语义转按压态 200ms。方向全对。
3. **滚动向上滑入顶栏、向下滑出**——把手势空间还给内容，且菜单是 bottom sheet 而非全屏遮罩（保留方位感），菜单内放放大版主题 Dimmer 控件解决"56px 顶栏放不下三档拨钮"的问题。

**缺点/风险：**

1. **⌘K palette 没有移动形态——桌面导航增强在手机上消失**（我的六项核查中唯一被点名的完整性缺口）：§7.1 的 palette 是桌面键盘体验的一部分，§11 的移动导航（wordmark + 主题钮 + 菜单钮）完全没提 palette 的 bottom-sheet 形态。G 的移动用户失去了"跳到任意 section"的最快路径，只剩菜单 sheet。对比 C/H 都给 palette 写了移动形态，这是方案内的不对称。
2. **菜单钮是"两条 hairline 组成的极简图标"——本质是汉堡**，只是画细了。bottom sheet 呈现目录比全屏炸场好，但导航形态的观点性弱于 A/B/D/F 的"文字按钮 + 全屏目录"与 E/H 的"检索优先"。在移动端，G 的导航答案是八个方案里最常规的。
3. **First Light 与 mix-blend-mode 的移动 GPU 成本被低估**：0.9s 的全屏径向渐变层做 scale + opacity 动画在 compositor 上确实便宜，但 H1 的 `::after` 斜向高光条用 `mix-blend-mode: plus-lighter`——blend mode 在部分移动 GPU 上强制离屏渲染，且方案只对 `blur > 8px` 设了 coarse-pointer 禁用，未对 blend mode 设。另外主题切换 700ms 锁输入在移动端可感（用户连点会被吞）。

**最值得被偷走的想法：按压即提亮的媒体反馈（hover 语义 → 200ms active 提亮）**——G 把"射灯移过来"的桌面 hover 隐喻翻译成按压瞬间的亮度反馈，材质语言在触屏上没有断掉。所有有图片压暗/提亮逻辑的方案都该定义这个按压态。

**375px 走查**：首屏 = eyebrow（关键词已内联，右侧铭牌砍掉——正确的移动取舍）+ display-1 44px（~4 行，无 balance 指定）+ subhead 段落 + 下滚箭头，First Light 0.9s。第一屏滚动后 = 01 Research 关键词墙（display-2 衬线行）。到达 Research = 滚动 ≈1 屏；到达 Work = 滚动 ≈2 屏或菜单 sheet → 2 次。移动端体验成立但无惊喜——最接近"响应式收缩"的一个（尽管收缩得很有教养）。

### Team H — Experimental「可检索的人」

**优点：**

1. **"移动端把 palette 升为主模式"是全场最大胆也最正确的移动导航重设计**（§11）：五个主链接不塞汉堡——进入 palette bottom sheet（56px 大行高）+ 页脚站点地图；顶栏只剩 wordmark + ⌕ + 主题。理由成立："拇指场景下'查询'比'扫菜单'更快"。这把移动端的结构性劣势（导航空间小）转化为方案核心隐喻的优势（检索即导航）。
2. **装置的触屏翻译完整且诚实**：拖柄 → 横向 swipe 卡位（四行纵向堆叠，swipe 或 tap 逐条揭示）、滚动映射保留、4s 提示改"swipe to reveal"、跳过锚点从第一秒就常驻、回访 resolved 记忆。证据链横改纵（纵向左轨线 = 移动端的"因果轴"，绘制方向向下一次性）。每个桌面交互都有成文的触屏等价物——与 C 并列触屏替代完整度第一。
3. **低端机减载写成机制**：玩具点数 24→16（`hardwareConcurrency` ≤4 探测）、装置 ≤6KB gzip、零 canvas/WebGL、`touch-action: none` 只在 8px 拖柄上。§15 的可用性守护清单（键盘地图、reduced-motion 全量表、无 JS、`prefers-contrast: more` 关遮蔽）是全场最完整的一张验收网。

**缺点/风险：**

1. **移动首屏是一场"仪式税"**（即使税率已尽量降）：首屏 = 标题 + 四行装置（名称可读、摘要 blur）+ 提示，信息密度低于任何对手——招聘者在手机上排队时扫到的是一个需要交互才完整的首屏。跳过锚点常驻 + 名称可读 + 滚动即推进，把税降到很低，但对比 A/D/F"滚动即内容"的首屏，H 的移动首屏仍然是八案中唯一"不交互则信息不完整"的（摘要是实质内容）。方案 §14.1 自认此风险并给了退化路径，我认可其自觉，但移动端应该更果断：建议移动端默认 resolved 态或首行预揭示。
2. **blur 滤镜在低端移动 GPU 的成本**：四行摘要的 `blur(5px)→0` 动画是小面积，但 blur 是移动 GPU 上最贵的 filter 之一；方案对 `prefers-contrast: more` 关遮蔽、对低端机减玩具点数，却没有对 coarse-pointer/低端机关闭 blur 过渡（240ms 内 blur 插值比静态 blur 更贵）。一个 `@media (pointer: coarse)` 关键帧降级即可补上。
3. **页脚站点地图作为 palette 的备份很弱**：palette 主模式意味着不打开 palette 的用户在移动端没有可见的 section 导航（顶栏无链接）——页脚要滚到最底才能到。对比 A/F 的全屏目录页按钮，H 把赌注全压在了 palette 可发现性上（chip 常显 + 一次性 toast + `/` 提示）。建议移动顶栏加第二个文字入口（如 `Index`）作为零成本保险。

**最值得被偷走的想法：移动端"palette 即导航"的架构决定**——把 command palette 从桌面彩蛋提升为移动端第一导航，bottom sheet + 56px 行高 + 分组结果。这是对"移动端导航 = 汉堡 or 底部 tab"二元论之外第三条路的完整论证。

**375px 走查**：首屏 = 顶栏（wordmark + ⌕ + 主题）+ 标题 40px（~3 行）+ 四行装置（名称清晰、摘要遮蔽、swipe 提示）。第一屏滚动后 = 揭示推进 + 01 Work 纵向证据链（问题→方法→产物→链接自上而下）。到达 Work = 滚动 ≈1 屏；到达 Research = 滚动，或 ⌕ palette 搜 "poisoning" = 1–2 次直达。搜索触达全场第一，但首屏信息完整度全场垫底。

## 排名与理由

**Top 3：A（Monograph 单行本）> C（精密仪器）> E（BENCH 工作台）**

- **第一 · A**：在我的两个否决区上双列全场第一——`mobile_experience` 9：Index 总目录页（非汉堡）、章节指示器（真重设计的证据）、正文为拇指放大到 17/30、Work 行两端对齐重排、hover→`:active` 全局映射、触控目标全篇成文；`performance` 9：零 Canvas、纯文字 LCP <1.2s（全场唯一"结构上必然达成"的 LCP 目标）、3 字体 ≤260KB、动效预算 ≤3。它的移动端哲学和桌面一致：删到只剩必须的，剩下的每个都是对的。失分点仅是无搜索的长期缺口与 375px Hero 断行预案缺失。
- **第二 · C**：`mobile_experience` 9（与 A 并列）：全场唯一把**两个**签名交互的触屏替代都写成制度（⌘K→抽屉顶部搜索框、hover 重排→长按演示 + 文本降级）、竖排 pipeline 瀑布读数、bottom-sheet Dossier + swipe 翻阅是移动端档案形态的最优解；`performance` 8.5：lazy 索引 12KB、SMIL 读数点、FLIP 三重禁用条件。排第二而非第一的原因：375×667 首屏重排件超载未定取舍、长按手势的系统冲突未处理、CJK fallback 抖动未覆盖——执行细节比 A 多三个未决项。
- **第三 · E**：`mobile_experience` 8.5 + `performance` 8：它是唯一敢把 Canvas 放上移动首屏又给出可信降级链的方案（节点减载、14ms 帧预算、sprite、自动降帧、双停机），"检索即移动第一导航" + 拇指区工具坞 + 源头禁 hover 依赖 demo 的意识全场最佳。排第三的原因：Canvas 方案的移动性能方差天然最大（降帧路径的存在即是自供），且主张行 44px 断行未做构图、segmented control 横滑有可发现性黑洞。它赢在工程勇气的质量，输在余量。
- 未能进入 Top 3 但值得记录：**F** 的 `performance` 9（<120KB 字体全场最轻）与"脊线 + GENERATION 降级"是全场最优雅的移动语言，但表格语法的详情深度（半屏展开面板、无独立详情页）在移动端最伤长期作品集阅读，`portfolio_presentation` 7.5 拖住了它。**D** 的移动黄金路径第一（Research 即首屏后第一节）、边注三段降级教科书级，但 CJK 衬线在移动设备的回退灾难与双 SVG 地图的维护税压低了我的两个高压维度。**H** 的"palette 即移动导航"是最有观点的架构决定，但移动首屏仪式税 + blur 成本未按触屏降级，在我的否决区被压住。**B** 的移动阅读链路（回放模式、行内边注、mini-folio）质量很高，但 4 字体家族 ≈260KB 是移动端最重的文字栈。**G** 是最接近"响应式收缩"的一个：堆叠规则有教养（标题先于媒体、srcset、coarse-pointer 禁 blur），但 palette 无移动形态、菜单是变体汉堡、移动端无签名观点。

## 给第二轮的三条移动端合并建议
